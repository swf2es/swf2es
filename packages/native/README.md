# @swf2es/native

swf2es's WebAssembly modules, one sub-path each, built with the
repository's pinned Zig:

- `@swf2es/native/bitmap`: BitmapData convolution kernels.
- `@swf2es/native/compress`: synchronous zlib and LZMA.
- `@swf2es/native/mp3`: synchronous MP3 frame decoding with minimp3.
- `@swf2es/native/tessellate`: double-precision libtess2 fill tessellation.

The package depends on no other package and uses no DOM or node APIs.
Each sub-path compiles and instantiates its own module, with its own memory
and lifetime, and loading one never loads another's binary.

## Building

The package is one Zig project inside the npm package: `build.zig` at its
root builds every binary, and each sub-path's Zig source, in `src/<sub-path>/`,
sits beside its TypeScript wrapper (`index.ts`) and its generated
`binary.ts`. tsc compiles only the `.ts` files, and only `dist/` and
`LICENSE.third-party` are published, so the Zig and C sources are in the
repository but not in the npm tarball. `include/` holds the libc headers
the vendored C includes, which wasm32-freestanding lacks: `string.h` maps
`memcpy`, `memmove` and `memset` to clang's builtins, which become bulk
memory instructions, and the rest declare only what the C calls.

The binaries are checked in, so ordinary builds need no compiler. `pnpm
build` verifies each one's input digest and the notices. To rebuild after
changing the sources or an upstream pin:

```sh
pnpm --filter @swf2es/native build:wasm
```

This runs the bitmap kernel's tests (`zig build test`) and then `zig
build` here with Zig 0.17.0, from the PATH or else downloaded once into
`~/.cache/swf2es` by `tools/zig.ts` and checked against its SHA-256, with
fresh caches, and writes each module into its `src/<sub-path>/binary.ts`
and the vendored C's notices, verbatim, into `LICENSE.third-party`. CI
rebuilds and compares the generated bytes. `zig build` alone, in this
folder, builds `zig-out/bin/*.wasm` like any Zig project (`.zig-cache/` and
`zig-out/` are ignored).

## bitmap

The web host uses these kernels by default, with the JS path as fallback;
`configure({ nativeBitmaps: false })` keeps new playbacks on JS and loads
no native bitmap code. The output is the same pixels either way. Each
playback owns its convolution scratch, instantiated on first use, and
releases it at teardown. AS3 and AVM1 BitmapData.applyFilter use the same hook;
GPU filters and other CPU filters are unchanged. Worker instances without a
hook keep using JS.

Direct hosts can create a `Convolver` and assign its `convolve` method to a
Scripting or Avm1 `bitmapConvolver`, then clear the hook and call `dispose()`
when that owner retires. The operation returns owned premultiplied ARGB
`Uint32Array` pixels or `null` for JS fallback. No source pixels are changed.
Results survive later calls, memory growth, rejection and disposal.

The wrapper convolves a rect a band of rows at a time, about 1 MiB of
input and output a call: it copies each band's rows plus the kernel's halo
and the coefficients in, and the band's output out before scratch is
reused. The kernel keeps straight-colour planes for only the kernel's rows,
so a call's scratch stays near 2 MiB even 4096 pixels wide, and a playback
filtering large bitmaps every frame keeps its instance. Existing player
code handles clipping, destination writing and notifications. Strict double
arithmetic and Flash's fixed-point 3×3 quirks match the existing JS path.
The kernel uses explicit f64x2 wasm SIMD, and there is no scalar build:
every current browser ships wasm SIMD (Chrome 91, Firefox 89, Safari 16.4
on), and an engine without it refuses the module just as one without Wasm
or under a CSP refusal does, which leaves the filter to the JS path. The
binary imports nothing. A refusal is tried once per owner, traps discard
the instance, and normal rejection can reuse its arena.

Wasm memory has a 128 MiB maximum. Instances above 8 MiB are dropped after a
call; `new Convolver({ retainMemory: bytes })` adjusts that threshold.
Arena reset reuses capacity; only dropping the instance permits its memory
to be collected.

The package's build first runs the kernel's Zig tests on the host (`zig
build test` in this folder): exact pixels for small cases, and every
allocation failing in turn. The kernel is `src/bitmap/convolve.zig`, taking
any `std.mem.Allocator`; `src/bitmap/root.zig` wraps it in the Wasm
module's bump arena. No external dependency is needed.

`node --test tests/unit/native-bitmap.test.ts` checks exact pixels, ownership,
rejection and trap fallback. `node tests/web/run.ts` checks both VMs, the default,
the opt-out, missing modules, blocked compilation, traps, CSP and teardown.

After `pnpm build`, run `node tests/player/bitmap-bench.ts [processes, 2]`
under the machine lock for synthetic full applyFilter timings in Chrome.
It includes input/output copying, destination writes and oversized-instance
recreation. The benchmark compares JS and native with exact output
checks and nine balanced rounds per fresh browser process. It measures CPU
filter calls; whole-game performance depends on their share of the workload.

## compress

Synchronous zlib and LZMA for SWF bodies, bitmaps and `ByteArray`, in one
WebAssembly module that imports nothing. Its upstream sources are pinned
submodules of swf2es's own repositories: zlib 1.3.2 in
[`vendor/zlib`](../../vendor/zlib) (https://github.com/swf2es/zlib, a fork
of madler/zlib, at tag `v1.3.2`), and the LZMA SDK 26.05 in
[`vendor/lzma-sdk`](../../vendor/lzma-sdk)
(https://github.com/swf2es/lzma-sdk at tag `v26.05`: the release as
published, line endings made LF, whose README names the archive and its
SHA-256). Of the SDK only the encoder and the decoder are compiled, all
public domain:

`src/compress/root.zig` exports the module's calls, gives zlib and the SDK a bump
arena through their allocator callbacks, and calls them through bindings
that `build.zig` translates from `zlib.h`, `LzmaEnc.h` and `LzmaDec.h`
(Zig 0.17 has no `@cImport`), with the same defines as it compiles the C
with, so a define cannot change a struct's layout on one side only.
wasm32-freestanding has no libc headers, so `include/` declares what the
C calls. Zig compiles C there with `-ffreestanding`, which would leave
`memcpy`, `memset` and `memmove` calls to compiler-rt's loops, so
`include/string.h` maps them to clang's builtins, which become bulk memory
instructions; `memcmp` and `strlen` come from Zig's compiler-rt.
Upstream sources stay unchanged.

- `inflate(data, raw, limit)` inflates a zlib or raw deflate stream to at
  most `limit` bytes, stopping at the stream's end.
- `deflate(data, level, raw)` deflates as zlib does at that level.
- `lzmaDecode(stream, size)` decodes an LZMA stream, its 5 property bytes
  first, to `size` bytes or to its end marker.
- `lzmaEncode(data)` writes `ByteArray`'s LZMA: properties, an 8-byte
  length and the stream, at level 9 with a 1 MB dictionary as avmplus, or
  a smaller one for less data.

Decoders return a status, the bytes decoded and how much input they read,
and can leave room before their output so that a SWF's header needs no
second copy. A failure gives the bytes decoded before it only when the
caller asks (`partial`), so a bomb that fails is never copied out of the
module; an output the page cannot allocate is `NO_MEMORY`. An instance
whose call threw is dropped too.

The module is compiled synchronously on first use from the base64 in
`src/compress/binary.ts`. Each call resets a bump arena in the module's memory,
copies its input in and its output out; outputs of unknown size grow in
place at the arena's top, so they are never copied as they grow. Memory
never shrinks, so an instance whose memory grew past 8 MiB, which LZMA
encoding of more than a few hundred KB does, is dropped after its call and the next call
instantiates a new one.

## mp3

Synchronous MP3 frame decoding with minimp3, in one WebAssembly module that
imports nothing. Its upstream source is the pinned submodule
[`vendor/minimp3`](../../vendor/minimp3) (https://github.com/swf2es/minimp3,
a fork of lieff/minimp3, at commit `ea99364`), compiled unchanged.

Call `await prepareMp3()` before running scripts. It compiles the embedded
WASM binary once, without instantiating a decoder or decoding any audio.
An `Mp3Decoder` then decodes a sequence of whole frames synchronously.
Its `pcm` view is overwritten by the next `read()`; copy samples out before
reading again. Each decoder owns a fixed 128 KiB workspace and imports
nothing from the host. The module is shared, but decoder state is not.

The player uses this only for `Sound.extract()`. It keeps the samples weakly
by sound, decodes on the first extraction, and preserves Flash's untrimmed
MP3 frame counts. Playback still uses the audio host's decoder.

minimp3 is a single header. `build.zig` translates its declarations for
`src/mp3/root.zig` (Zig 0.17 has no `@cImport`) and compiles its implementation
from a generated one-line C file that defines `MINIMP3_IMPLEMENTATION` and
includes it, both with the same defines (`MINIMP3_ONLY_MP3`,
`MINIMP3_NO_SIMD`, `MINIMP3_FLOAT_OUTPUT`), so the sample type cannot
differ between the two. The implementation stays C, compiled by Zig's
clang with `-ffp-contract=off`, rather than translated to Zig, so the
samples are the same arithmetic as before.

wasm SIMD was measured and left off: with the `simd128` feature, LLVM
vectorises enough of minimp3 to decode about 12% faster (some 405 ms
against 460 for 22,854 frames) with bit-identical samples, but the module
grows by 12.7 KB and would need SIMD of every engine. minimp3's own SIMD
is SSE and NEON only, which `MINIMP3_NO_SIMD` keeps off.

Where the module does not compile, `prepareMp3()` still resolves,
`mp3Available()` is false, and the player plays on: `Sound.extract()`
writes no samples for an MP3, as Flash does for a sound it cannot decode.

## tessellate

This compiles the small double-precision patch in `vendor/libtess2`.
`build.zig` compiles the vendored C and the arena/API adapter in
`src/tessellate/root.zig` together, translating the C header with
`b.addTranslateC`, as for MP3 and compression. libtess2 remains under SGI
Free Software License B.

`@swf2es/web` uses native fills by default. Each playback lazily loads and
owns a tessellator, then releases its scratch on teardown.
`configure({ nativeFills: false })` keeps new playbacks on the JS path and
skips native loading. Missing modules or unavailable Wasm also use JS.

When constructing a `PixiView` directly, opt in through its generic hook:

```ts
import { PixiView } from "@swf2es/player";
import { Tessellator } from "@swf2es/native/tessellate";

const tessellator = new Tessellator();
const view = new PixiView(renderer, { fillTessellator: tessellator.tessellate });
```

The player retains its existing curve flattening, paint and draw order.
It passes every contour of one fill together, using even-odd or non-zero
winding, with non-zero for masks. Rejection or an exception selects the
existing JS fill construction. The chosen result is retained by the
context factory so copies do not retry the tessellator. Dynamic drawings
and morph ratios construct new results when their contents change.

Each native call copies positions and indices into JS-owned typed arrays.
Positions remain doubles; indices use 16 bits through 65,536 vertices and
32 bits above that. A native layer's position views share a contiguous owned
buffer, which Pixi can retain directly when the draw transforms are identities.
No cached geometry aliases Wasm scratch. Pixi consumes these through
`GraphicsContext.fillGeometry`, generating the usual paint UVs and batches;
the immutable source buffers survive path retirement and context restoration.
The hook also accepts another tessellator with the same structural result.

The absolute memory ceiling is 128 MiB, including static data, the C stack
and the arena. Instances above 8 MiB are discarded after the call. Options
can lower the limit or retained capacity. Invalid
coordinates (including values outside ±2^23), malformed contours, more
than one million input vertices, allocation failure and native failure
return `null`. A throwing failure import replaces libtess2's longjmp;
that instance is always discarded before another call. Arena reset alone
does not shrink Wasm memory. `dispose()` drops retained scratch without
affecting previous output.

Different triangle layouts can change subpixel edge coverage and interior
gradient or bitmap interpolation. At low quality this can switch a whole
boundary pixel. AIR comparisons do not show either backend consistently
closer to Flash; enabling native fills accepts these differences.

Run the player references and context-loss checks with
`SWF2ES_NATIVE_FILLS=1` to exercise the native hook in those tests.
`node tests/fuzz/tessellate.ts [cases] [seed]`
checks both fill rules against independent ray crossings; the default test
suite includes 2,000 fills and 24,000 coverage samples. Synthetic fixtures
also check coincident edges, holes and detail at large coordinates.
